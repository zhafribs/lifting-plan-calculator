# A saved plan file

**Date:** 2026-11-28
**Status:** proposed — no code until approved

## Problem

Nothing is stored between launches. Closing the app loses the plan, and there is
no way to hand one to a colleague or return to it next week. The privacy
contract makes that deliberate, so any storage has to be explicit and visible.

## Goal

- An explicit **Save plan…** and **Open plan…**, both to a path the operator
  chooses in the system dialog.
- One JSON file carrying the plan's inputs and the report settings. Results are
  recomputed, never stored.
- The file is untrusted input: it is fully validated before anything is applied,
  and a bad file changes nothing.
- Nothing is written unless the operator chooses Save; no recent-files list, no
  auto-save, no telemetry.
- Opening a saved plan and printing it reproduces the plan that was saved.

## Non-goals

- Auto-save, a recent-plans list, cloud storage, or a database.
- Several lifts in one file (that is product decision 2).
- Unit conversion (product decision 3).
- Saving solved results, the PDF, or the diagram bitmap.
- A dirty-state prompt on close. Closing still discards, exactly as today.

## File format

A UTF-8 JSON object, suggested name `<reference>.lpc.json`:

```json
{
  "format": "lifting-plan-calculator/plan",
  "version": 1,
  "state": {
    "load_items": [],
    "tackle_items": [],
    "crane": {},
    "outrigger": {},
    "sling": {},
    "nonuniform": {},
    "tandem": {}
  },
  "report": {
    "sections": ["plan", "crane", "lines", "outrigger"],
    "page_breaks": ["crane"],
    "signoff": {
      "reference": "LP-2026-001",
      "prepared_by": "",
      "checked_by": "",
      "approved_by": ""
    },
    "footer_text": "Prepared with Lifting Plan Calculator …",
    "margins": { "top": 25.4, "right": 25.4, "bottom": 25.4, "left": 25.4 },
    "diagram_scale": 50,
    "issued_at": "28-11-2026"
  }
}
```

- `state` is the same wire shape the UI sends to `solve_all` (`AppState`), so
  the file and the live state cannot drift.
- `report.sections` are the report's section keys; `page_breaks` are the keys
  that start a new page. Both are validated against the known keys.
- `margins` are millimetres, `5..50` each, and must leave at least 60 mm of
  sheet.
- `diagram_scale` is `25..100`.
- `issued_at` is the report's date (`DD-MM-YYYY`); a saved plan keeps its issue
  date, a new plan gets today's.
- Not saved: theme, window size, current tab, zoom, toasts, solved results, the
  last export path, and the workbook's full table view (`chart_table`). The crane
  keeps the chart points at the selected boom, the boom/radius lists and the
  chart label, so the check and the report are complete; the table is a view of
  the original workbook and returns only when that workbook is re-imported.

## Design

### Rust: the trust boundary

Two commands beside `save_pdf`/`save_html`, with the same `rfd` dialog pattern:

- `save_plan(state: AppState, report: PlanReport, suggested_name: String)
  -> Result<Option<String>, String>` — save dialog, force the `.json`
  extension, validate, write once with `write_all`, return the path or None on
  cancel.
- `open_plan() -> Result<Option<PlanFile>, String>` — open dialog, read at most
  the size cap, parse, validate, return the whole plan or an error. The frontend
  never parses the file.

Validation, in this order:

1. File size ≤ 4 MiB.
2. `format` is exactly `lifting-plan-calculator/plan`.
3. `version` is `1`. Any other number is refused with a message naming the
   version (a newer plan needs a newer app).
4. The seven top-level `state` keys and the `report` object are present.
5. Every number is finite and inside the bound its control uses: weights and
   capacities `0..1e7`, lengths `0..1e6`, positions `±1e6`, angles `0..360`,
   quantities `0..1e6`. Missing leaves take the same defaults as the live wire.
6. Every catalog key exists: `load_type` (`fixed`, `per_metre`, `volume`),
   `chart_source` (`""`, `excel`), `ground_key`, `hitch`, `pad_shape`,
   `thickness_material`, `angle_basis`, `jib_config`, tandem methods.
7. String lengths: names, lift names and labels ≤ 500 characters; the footer
   ≤ 500; no control characters other than tab/newline in the footer.
8. `load_items` and `tackle_items` ≤ 500 each; `chart_points` ≤ 50,000;
   `rows` ≤ 10,000; line `id`s are unique and non-zero.
9. `sections` and `page_breaks` are known keys; `margins` and `diagram_scale`
   are in range.

A refusal names the field and never returns a half-built plan. The save path
validates the same structure before writing, so the app cannot produce a file it
would refuse to open.

### Frontend: where it lives

- The **Summary** screen owns the report settings, so **Save plan…** and
  **Open plan…** join its existing actions.
- Save passes `store.state` and a `reportSettings()` object; the returned path
  is shown in a success toast.
- Open calls `open_plan()`, then applies atomically: `store.setState(state)`,
  then the report settings (section switches, new-page switches, sign-off
  fields, footer, margins, diagram scale, issue date), then rebuilds the
  preview. `lastSavedPath`/`lastSavedHtml` are cleared.
- Failure: one error toast with the command's message; the current plan is
  untouched.
- The success toast for Save is the app's only feedback; there is no “saved”
  indicator, because nothing is tracked between launches.

### Docs to update when it lands

- `AGENTS.md` privacy contract: “nothing is stored between launches” becomes
  “nothing is stored unless you save a plan file”; the update check and
  `ui.log` stay the only automatic writes.
- README scope/privacy wording.
- `docs/product-decisions.md` decision 1 moves from open to decided.

## Acceptance

- Save a plan, close the app, reopen it, open the file: every input, section,
  sign-off line, margin, scale and the issue date match, and the printed PDF is
  the same as before saving.
- A plan saved by a future format version is refused with a message naming the
  version; the current plan is unchanged.
- A truncated or wrong `format` file, an out-of-range number, a catalog key that
  does not exist, duplicate line ids, and a 5 MiB file are each refused, and the
  current plan is unchanged in every case.
- Save is the only new write; no file appears anywhere else. Cancel writes
  nothing.
- Rust tests cover a round trip, each refusal above, and the size cap; the file
  stays under the cap for a plan with a full workbook chart.
- Manual: open a saved plan on a second machine, print it, and compare the PDF
  with the original.

## Risks

- A workbook chart can be large; the `chart_points` cap and the 4 MiB size cap
  must be checked against a real workbook before landing.
- `issued_at` frozen at save time will surprise someone who reopens a plan next
  month; the field is explicit and the help text should say so.
- Users may still expect auto-save. The buttons and the absence of a “saved”
  state must make the explicit model clear.
- The sign-off strings are printed into the report; the HTML builder's escaping
  is existing behaviour, and the Security seat must confirm a plan file cannot
  inject markup through them.
- Adding a user-chosen write is a real change to the privacy contract; the ADR
  and the README must say it in the same words.
